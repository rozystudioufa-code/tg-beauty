### 1. beauty-app.ru (Frog Studios)
**Тип:** Настоящий Telegram Mini App (WebApp-интерфейс внутри Telegram)  
**Ниша:** Все бьюти-услуги — салоны, спа, массаж, косметология, тату, перманент  
**Бот:** @Frog_studios_contact_bot | **Цена:** 3 000 ₽/мес, 7 дней бесплатно

**Что делает:**  
Подписочная Mini App платформа для бьюти-бизнеса. Клиент подписывается на канал мастера/салона, получает доступ к приложению внутри Telegram. Онлайн-запись, синхронизация с YClients, программа лояльности с баллами и уровнями.

**Сильные стороны:**
- Настоящий WebApp интерфейс — не чат с кнопками, а полноценный мобильный экран
- Интеграция с YClients CRM — расписание ведётся там, Mini App — витрина поверх
- Геймифицированная лояльность: уровни, задания, бонусы за активность
- Персональные уведомления о днях рождения, рассылки
- Доказанные результаты: +3x конверсия, 76% записей без участия администратора

**Слабые стороны:**
- Требует YClients (857 ₽/мес) как зависимость — дорого для соло-мастера
- Подписочная модель (3 000 ₽/мес) нецелесообразна для одного мастера
- Интерфейс скопирован с общих шаблонов салонов, без кастомизации под конкретный стиль
- Нет портфолио работ / галереи конкретного мастера

**Что мы можем сделать лучше:**
- Спроектировать под конкретный профиль соло-мастера по ресницам — с акцентом на визуальный каталог работ
- Убрать зависимость от YClients — собственное расписание слотов
- Добавить галерею «до/после» прямо в карточке услуги
- Сделать личный бренд мастера центром интерфейса, а не абстрактный «салон»

### 2. Telegram Salon Booking Bot (nazgool97 / GitHub)
**Тип:** Настоящий Telegram Mini App + классический бот  
**Ниша:** Салоны красоты, барбершопы, малый сервисный бизнес  
**GitHub:** github.com/nazgool97/telegram-salon-booking-bot | **Цена:** One-time (Gumroad)

**Что делает:**  
Самостоятельно разворачиваемый шаблон booking-системы. Двойной интерфейс: классический бот с кнопками + полноценная мобильная Mini App. Развёртывается через Docker.

**Сильные стороны:**
- Полный флоу записи экранами: каталог → мастер → дата → слот → подтверждение → оплата
- История визитов и корзина для нескольких услуг сразу
- Клиент держит все данные на своём сервере (приватность)
- Mobile-first подход, Telegram-нативный опыт

**Слабые стороны:**
- Требует технических знаний для деплоя (Docker, VPS)
- Нет готового визуального дизайна — «серый» интерфейс без эстетики
- Нет специфики для ресниц: всё сделано как generic-решение для любого мастера
- Отсутствует портфолио/галерея работ мастера

**Что мы можем сделать лучше:**
- Взять структуру экранов как основу — она правильная
- Добавить визуальный слой: категории видов наращивания, фото-референсы в карточках услуг
- Ориентировать дизайн на эстетику beauty-ниши (нежные цвета, типографика, фото работ)

### 3. @BeautyRussiaBot — Маркетплейс бьюти-мастеров
**Тип:** Telegram-бот (классический), не Mini App  
**Ниша:** Агрегатор — ногти, ресницы, брови, весь beauty-сегмент  
**Бот:** @BeautyRussiaBot | **Цена:** Бесплатно для мастеров и клиентов

**Что делает:**  
Агрегатор, соединяющий мастеров с клиентами. Мастера размещают анкеты с фото, адресом, ценами. Клиенты фильтруют по опыту, цене, городу. Взаимная система рейтингов. Также есть разделы для учебных курсов и поиска моделей.

**Сильные стороны:**
- Охват: нейл, ресницы, брови — всё в одном месте
- Поиск с фильтрами: опыт мастера, ценовой диапазон, геолокация
- Двусторонние рейтинги (мастер оценивает клиента тоже)
- Напоминания за 5 и 2 часа до записи
- Бесплатно — нет барьера входа для мастеров

**Слабые стороны:**
- Только чат-интерфейс, не Mini App — морально устаревший UX
- Нет визуальной витрины работ — только текст и фото в анкете
- Агрегатор = конкуренция с другими мастерами в ленте
- Нет возможности записи с оплатой — только контакт

**Что мы можем сделать лучше:**
- Создать персональное приложение конкретного мастера, а не быть в общем агрегаторе
- Дать мастеру собственный брендированный каталог с галереей работ
- Реализовать запись + оплата депозита прямо в приложении

### 4. CityBite — Food Delivery Mini App
**Тип:** Настоящий Telegram Mini App  
**Ниша:** Доставка еды / ресторан (смежная ниша — каталог + заказ)  
**Результаты:** +420% объём заказов, -70% комиссии, 70% заказов через Telegram

**Что делает:**  
Приложение для заказа еды с доставкой без посредников. Ключевое решение: вместо регистрации — сразу Telegram ID как аккаунт. Каталог меню → корзина → Telegram Pay → подтверждение в чате.

**Сильные стороны:**
- Zero-friction onboarding: никакой регистрации, имя и ID берётся из Telegram
- Категорийные табы (супы, салаты, горячее) — моментальная навигация
- Подтверждение заказа — сообщением в бот-чат, а не пуш-уведомлением
- Telegram Pay — оплата без выхода из Telegram
- Скелетон-экраны при загрузке — ощущение скорости

**Слабые стороны:**
- Специфично для ресторана — нет концепции «мастер» или «мастер + клиент»
- Каталог не адаптирован для услуг с длительностью и временными слотами
- Корзина создаёт сложность, которая не нужна для записи к мастеру

**Что мы можем сделать лучше:**
- Полностью скопировать паттерн нулевой регистрации
- Взять идею категорийных табов для видов наращивания (Классика / Объём / Мегаобъём / Цветное)
- Реализовать подтверждение записи как бот-сообщение в чат — высокий open rate
- Встроить Telegram Pay для депозита при записи

### 5. TeleVenue — Бронирование площадок (призёр конкурса Telegram)
**Тип:** Настоящий Telegram Mini App (3-е место официального конкурса Telegram)  
**Ниша:** Бронирование залов / площадок для мероприятий  
**GitHub:** github.com/NickNaskida/TeleVenue | **Стек:** React + Vite + TailwindCSS + FastAPI

**Что делает:**  
Каталог площадок с фильтрами → карточка с фото и деталями → форма бронирования с выбором слота → подтверждение в боте.

**Сильные стороны:**
- Победил в конкурсе Telegram — признанный эталон полноценного Mini App
- Фильтруемые карточки (тип, вместимость, цена) — паттерн прямо переносится на каталог мастеров
- Выбор слота с календарём — готовая ментальная модель для записи к мастеру
- Стек React + TailwindCSS + themeParams = проверенная архитектура
- Открытый исходный код — можно изучать детали реализации

**Слабые стороны:**
- Нет специфики бьюти — только бронирование площадки, без концепции «мастер»
- Нет оплаты депозита
- Нет напоминаний и повторной записи

**Что мы можем сделать лучше:**
- Перенести паттерн «карточка → детали → слот → подтверждение» напрямую
- Добавить галерею работ мастера в детальную карточку
- Реализовать напоминания за 24ч и 2ч через бот
- Добавить «Записаться снова» с одним тапом для повторных клиентов

## Обязательные UI-элементы

### Навигация
- **Нижняя навигационная панель** (3–4 вкладки): Главная, Услуги, Записи, Профиль
- **Нативная кнопка Back** (Telegram BackButton API) — кастомные кнопки «назад» запрещены
- **MainButton** (нативная кнопка Telegram снизу) — единственный способ двигаться вперёд по флоу записи
- **Индикатор шагов** в процессе записи: «Шаг 2 из 4»

### Карточки и контент
- **Карточка услуги**: фото, название техники, длительность, цена, кнопка «Записаться»
- **Горизонтальная полоса дат** (не полный календарь — слишком мелко на телефоне)
- **Сетка временных слотов** — цветовое кодирование: доступен / занят / выбран
- **Категорийные чипы / табы** (Классика / Объём / Цветное / Уход) — горизонтальная прокрутка
- **Бейджи срочности**: «Осталось 2 слота», «Популярно», «На этой неделе 3 места»

### Состояния и обратная связь
- **Скелетон-экраны** при загрузке данных — не белый экран со спиннером
- **Пустые состояния** с CTA — «Нет свободных слотов → Встать в лист ожидания»
- **Анимация успеха** при подтверждении записи (Lottie или CSS)
- **Haptic Feedback** при выборе слота и подтверждении записи

### Telegram-специфика
- **themeParams** — синхронизация со светлой/тёмной темой Telegram (обязательно)
- **ClosingConfirmation** — защита от случайного закрытия на шаге оплаты/подтверждения
- **CloudStorage** — сохранение состояния формы при переключении между чатами
- **Бот-сообщение** с подтверждением записи и напоминаниями (open rate ~100% vs push)

## Экспертная оценка

---

### Взгляд UX-дизайнера

#### Топ-5 ошибок новичков (убивают конверсию)

- **Портфолио спрятано за флоу записи.** Фото — это и есть решение о покупке. Пользователь, который не видел разницу между «3D Объём» и «Мегаобъём», не нажмёт «Записаться» — он выйдет и спросит подругу.
- **Слоты без контекста длительности.** Показывать «10:00 / 11:00 / 12:00» без указания длительности сеанса — значит разрушить доверие к расписанию. Классика занимает 1,5 часа, Мегаобъём — 3 часа. Это разные вещи.
- **Депозит появляется слишком поздно.** Если сумма депозита всплывает только на экране подтверждения — после того как клиент уже выбрала дату — это воспринимается как обман. Показывать депозит нужно на карточке услуги, до входа в флоу.
- **Нет пути отмены/переноса на этапе записи.** Клиент должна видеть условия отмены ДО оплаты депозита, а не в боте после. Иначе осторожные первичные клиенты уходят.
- **Кастомная кнопка «Назад» вместо Telegram BackButton API.** Конфликт с системным жестом смахивания назад закрывает всё приложение в середине записи.

#### Что обязательно (по приоритету)

1. **Фото «до/после» на каждой услуге** — не общая галерея, а свайп-сравнение конкретно по технике. Без этого конверсия у первичных клиентов стремится к нулю.
2. **Длительность + депозит видны на карточке** — до входа в воронку записи.
3. **`BackButton` API на каждом экране** — каждый экран регистрирует свой обработчик.
4. **Sticky-сводка внизу при выборе даты** — услуга и цена видны пока клиент листает слоты.
5. **Подтверждение записи приходит в бот-чат** — не только в приложении: клиент закроет Mini App и потеряет данные.

#### Что бесит пользователей в реальных приложениях

- Календарь, где все даты кликабельны, но половина уже занята — это выясняется после тапа. Недоступные слоты должны быть серыми сразу.
- Фото открываются во встроенном браузере, а не в нативном просмотрщике Telegram — ломает контекст.
- Запрос телефона, когда Telegram ID уже есть. Немедленная потеря доверия.
- Часовой пояс не указан явно. Мастера нередко принимают клиентов из других городов.

#### Скрытые ловушки Telegram Mini App

- **Высота viewport ≠ высота экрана.** Клавиатура сдвигает viewport вверх. Поля ввода, расположенные внизу, перекрываются. Использовать только `viewportStableHeight`.
- **Тема может измениться прямо во время сессии.** Жёсткие цвета без `themeParams` — нечитаемый текст у половины пользователей.
- **`MainButton` имеет состояние загрузки** — не использовать его значит получить двойные тапы и двойные записи.

#### Смелая рекомендация, которую никто не делает

**Вход через результат, а не через название услуги.** Первый экран — 6–8 фото-результатов: «Натуральный дневной», «Драматичный вечерний», «Цветной акцент». Клиент тапает на нужный результат — приложение само рекомендует услугу, длительность и цену. Название «Классика 1:1» ничего не говорит первичной клиентке. Фото того, что она хочет, конвертирует мгновенно.

### Взгляд маркетолога

#### Что заставляет записаться

- **Фото «до/после» должны показывать лицо, а не только ресницы крупным планом.** Женщины идентифицируют себя с целым образом. Реальная трансформация с контекстом («натуральный look для офиса, 1,5 часа») конвертирует лучше, чем макрофото.
- **Первый экран должен отвечать на вопрос: «Это для меня?»** Одна фраза, передающая стиль и личный бренд мастера — не «записаться на наращивание», а что-то, что создаёт ощущение «это мой мастер».
- **Выбор слота создаёт обязательство.** Показать календарь ДО меню услуг — как только клиент «застолбила» время в голове, она достраивает остальное. Это работает лучше классического флоу.
- **Депозит = «я держу это время только для вас»**, а не защита от no-show. Такой фрейминг переводит потерю в пользу клиента.
- **Один живой отзыв с именем и фото — прямо над кнопкой «Записаться»**, а не на отдельном экране с отзывами, куда никто не заходит.

#### Главные убийцы конверсии

- Слишком много вариантов услуг сразу — прайс-лист вместо витрины. Группировать: «Натуральный / Объёмный / Цветной».
- Расплывчатый призыв «Выберите удобное время». Работает: «Ближайшее время: пятница, 11:00» — один тап.
- Депозит без объяснения «зачем». Одно предложение с причиной убирает большую часть отказов.
- Нет обращения к тревоге первичной клиентки. Женщины, которые идут к новому мастеру, боятся потратить деньги и получить плохой результат. Одна фраза о том, что мастер берёт ответственность за итог, снимает этот барьер.

#### Копирайтинг (российский beauty-рынок)

- **Работает:** конкретика с деталью («объём 3D, держится 4 недели», «работаю без запаха клея — для чувствительных глаз»), intimacy («мои клиентки», «я сама ношу этот формат каждый день»)
- **Не работает:** «профессиональный мастер», «высококачественные материалы», «индивидуальный подход» — эти фразы отфильтровываются автоматически, они у каждого конкурента
- **Дефицит — только для постоянных клиентов.** «Осталось 2 места!» для первичных читается как давление и сигнализирует о слабом спросе. Для тех, кто уже доверяет — работает отлично.

#### Удержание клиентов

- **Нарратив прогресса.** После каждого визита бот: «Это ваш 3-й визит...» — клиентка чувствует, что строит что-то, а не просто покупает услугу.
- **Голос мастера, не системы.** «Жду вас завтра в 11 — напомните мне, если нужна парковка» удерживает несравнимо лучше, чем «Напоминание: ваша запись 20 мая».
- **Статус, не скидка.** Значок «Постоянная клиентка» конвертирует лучше баллов — статус нельзя перенести к конкуренту.

#### Недооценённая тактика роста

**Момент шеринга сразу после визита.** Отправить сообщение через 2 часа после сеанса — когда клиентка ещё показывает ресницы коллегам и хочет похвастаться — с персональной карточкой и реферальной ссылкой одним тапом. Большинство мастеров просят отзыв. Никто не ловит **пик эмоции**, когда клиентка сама хочет рассказать всем. Это окно — 2–4 часа после визита.

### Взгляд Telegram-разработчика

#### Реальные ограничения платформы

- **Нестабильность viewport — главная боль.** На iOS `window.innerHeight` врёт. Использовать только `WebApp.viewportStableHeight` для расчётов макета. Поля ввода и date-пикеры в нижней части экрана сломаются на iOS до тех пор, пока это не учтено.
- **`CloudStorage` — асинхронный и медленный.** Каждая операция — отдельный round-trip до серверов Telegram. Не использовать для сохранения состояния на каждый keystroke. Батчить записи, сохранять только при переходе между шагами.
- **Нет фоновой обработки.** Как только Mini App закрыта — ничего не работает. `sendData()` моментально завершает приложение. Если бэкенд не подтвердил запись до этого вызова — гонка состояний.
- **Прерывания платёжного флоу.** `openInvoice()` открывает нативный оверлей. Если пользователь свернёт приложение в момент оплаты — надёжного колбэка нет. Статус оплаты нужно reconcile на сервере через bot webhook, а не только через client-side callback.
- **Фото-галереи тяжёлые.** Карусели «до/после» в полном разрешении внутри Telegram WebView заметно тормозят на бюджетных Android. Lazy loading и WebP с ограничением размера — с первого дня.

#### Что работает отлично

- **Zero-auth через `initData`** — настоящее конкурентное преимущество. Серверная валидация HMAC даёт верифицированную личность при первом открытии.
- **`MainButton` как двигатель прогресса** — клиент не ищет кнопку. Включать/выключать реактивно по мере прохождения валидации.
- **Бот-уведомления бьют email у этой аудитории наголову.** Подтверждение, напоминание за 24ч — всё в чате без каких-либо opt-in разрешений.
- **Deep links через `startapp`** — можно прилинковать прямо на конкретную услугу или слот из поста в канале. Удобно для акций.

#### Конкретные ловушки в планируемом API

- **`initDataUnsafe` — только для клиента, легко подделать.** На бэкенде всегда валидировать HMAC строку `initData` через токен бота. Это не опционально.
- **`BackButton` конфликтует с browser history.** Если используется React Router с `history` — кнопка «назад» сработает и в Telegram, и в браузере. Решение: Telegram BackButton как единственный источник навигации, без `history.push`.
- **`HapticFeedback` молча игнорируется на desktop и некоторых Android-скинах.** Никогда не ждать ответа, не обрабатывать ошибки — fire and forget.
- **`ClosingConfirmation` остаётся активным между сессиями**, если не отключить после завершения записи. Пользователь получит подтверждение закрытия даже при следующем открытии с нуля.
- **Цвета в `themeParams` могут приходить без `#` на старых версиях Telegram.** Мост с CSS-переменными TailwindCSS должен обрабатывать оба формата.

#### Оценка стека

React + Vite + tma.js — надёжный выбор. Хуки `@tma.js/sdk-react` чисто абстрагируют реактивность viewport и темы. TelegramUI — правильное решение, компоненты уже настроены под визуальный язык Telegram.

Один реальный gotcha: **компоненты `List` и `Cell` в TelegramUI имеют проблемы со скроллом в Telegram iOS WebView.** Добавить `-webkit-overflow-scrolling: touch` и тестировать scroll-контейнеры отдельно.

#### Архитектурные решения, которые дорого менять потом

- **Серверная валидация `initData` — до первого booking-эндпоинта.** Retrofit болезнен.
- **Idempotency keys на всех мутациях записи.** Сеть внутри WebView ненадёжна — двойные тапы реальны.
- **Стратегия блокировки слотов — определить до написания кода.** Оптимистичная (показать доступным, отказать при подтверждении) vs. пессимистичная (заблокировать при выборе, TTL-освобождение). Для соло-мастера с ограниченными слотами — пессимистичная правильнее.
- **Bot webhook и бэкенд Mini App должны разделять одну state machine записи.** Два сервиса, каждый из которых частично владеет состоянием — дивергируют. Один сервис, одна машина состояний.
